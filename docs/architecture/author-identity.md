# 作者と外部アカウント

作者の管理名と外部サービスのプロフィール情報を分ける。作者の主キーはローカルUUIDで、メディアはこのUUIDに関連付ける。外部アカウントの更新でメディアの作者IDを変更しない。

## 保存先と識別

| 情報 | 保存先 | 用途 |
| --- | --- | --- |
| 作者UUID・管理名 | `authors.id` / `authors.name` | ローカルでの管理・メディアの関連付け |
| プラットフォーム | `author_accounts.platform` | サービスごとの名前空間。旧情報で不明ならNULL |
| 固定の外部ユーザーID | `author_accounts.remote_id` | 同一アカウントの識別。Twitterは数値を文字列で保存 |
| ユーザー名・クリエイター識別子 | `author_accounts.account_id` | 現在のhandle/slug。既存入力との互換のためカラム名を維持 |
| 外部の表示名・プロフィールURL | `author_accounts.display_name` / `profile_url` | プロフィール表示 |
| 情報を取得した日時 | `author_accounts.observed_at` | 古い情報による上書きを防ぐ。投稿日時とは別 |

`authors.account_id` は削除する。APIの `Author.accountId` は既存クライアント用の派生値で、保存先ではない。複数アカウントを扱うクライアントは `Author.accounts` を利用する。作者スキーマは `core/domain/authors/schemas.ts` に集約し、mediaからは互換re-exportする。Repositoryは `IAuthorRepository` / `createAuthorRepository` に統一する。

## Twitterで表示名・ユーザー名が変わった場合

[XのUser Lookup](https://docs.x.com/x-api/users/lookup/introduction)は `id`、`name`、`username` を別フィールドとして返す。[公式データ辞書](https://docs.x.com/x-api/enterprise-gnip-2.0/fundamentals/data-dictionary)は変更される名前・handleではなくユーザーIDを主識別子にするよう案内している。[ユーザー名変更のヘルプ](https://help.x.com/en/managing-your-account/change-x-handle)によると、以前のユーザー名は別アカウントが使用できる。

- `platform + remoteId` が同じなら同一外部アカウント。新しい取得日時のユーザー名・表示名・URLを更新する。
- 作者管理名が以前の外部表示名と一致している場合は、新しい表示名に追従する。ユーザーが別の管理名に編集した場合は、その管理名を維持する。
- 異なる固定IDが同じユーザー名を使っていても、別アカウントとして保存する。
- 固定IDのない既存データは未確認のアカウントとして保持する。ユーザー名一致だけで固定IDのある作者に自動統合しない。旧アカウントのhandleだけでは、改名と別人による再利用を判別できないため。
- 取得日時のあるプロフィールを、より古い日時または取得日時のない入力で上書きしない。
- 投稿や旧JSONのURLは取得時の出典として保持し、プロフィール更新で書き換えない。

xtracterはXが既に取得したGraphQLレスポンスから、投稿IDごとの投稿者ID・プロフィールを取得する。追加のAPIリクエストは行わない。引用投稿は別の投稿IDで保持し、画像を取り込む投稿のIDに一致する情報だけを使用する。引用画像では画像自身のパーマリンクを優先し、外側の投稿者名・本文・日時を流用しない。数値IDをJavaScriptのNumberへ変換しない。レスポンス形状が非対応、取得が間に合わない、ユーザー情報が省略されている場合は、固定IDなしの取り込みを続ける。この場合、改名の自動追跡は保証できない。

## 過去の誤登録を修正する

### 現在の@ユーザー名から固定IDを確認する

Managerで作者のアカウントを選び、「現在のXユーザー名」に現在のhandleを入力して「プロフィールを取得して確認」を押す。旧データのプラットフォームが不明でも、この操作でXアカウントとして確認できる。

外部アカウントが未登録の作者にも、同じ画面から確認済みXアカウントを追加できる。この場合も既存の作者UUIDとメディアの関連付けを維持する。

1. ダイアログの「Xプロフィールを開いて取得」を押す。更新済みxtracterをインストールし、その接続先をManagerと同じサーバーに設定しておく。
2. xtracterは開いたプロフィールの `UserByScreenName` レスポンスから固定ID・現在のユーザー名・表示名だけを取得する。確認用リンク以外のプロフィール情報をサーバーへ送信しない。
3. Managerへ戻り、取得結果と元の作者を照合する。「元の作者と同じアカウントであることを確認しました」にチェックして更新する。

取得結果は10分間の仮保存で、この時点ではDBを変更しない。確認ボタンで既存アカウントに固定IDを登録し、作者UUID・メディアの関連付け・独自の管理名を維持する。以降の取り込みでは `platform + remoteId` で自動照合し、新しいプロフィールを反映する。別の作者に同じ固定IDが登録済みの場合は、先に明示的な作者統合が必要。登録済み固定IDと異なる結果、および確認中に変更されたアカウントは上書きしない。

APIトークンは不要。Xへのログインや拡張機能が利用できず取得できない場合は設定を確認して再取得する。確認用リンクを開いたブラウザにxtracterが必要で、サーバー再起動後は確認を開始し直す。定期巡回によるプロフィール更新は行わない。

### メディアの関連付けを修正する

Manager → 作者・外部アカウントから操作する。

1. 修正対象の作者を選ぶ。外部アカウント情報と固定IDの有無を確認する。
2. 必要ならソースを絞り、メディアのプレビュー・ファイル名・登録済み作者・出典URLを照合する。
3. 正しい作者を選ぶ。候補がなければ新しく登録する。確認できた固定IDだけを入力する。
4. メディアを選択し、確認ダイアログから作者を付け替える。または指定した誤った作者だけを外す。他の共作者は維持する。

一度に選択・修正できるのは表示中の最大50件で、APIの上限は100件。修正はトランザクションで実行し、選択したメディアから元作者が既に外れていた場合は全件を中止する。

**作者の統合**は別の操作。同一人物と確認できた作者の全メディア・外部アカウント・作者タグを修正先へ移し、元作者を削除する。ソース絞り込みやメディア選択には限定されない。関連付けの重複は作成しない。固定IDのない旧作者を固定IDのある作者へ結び付けるときも、この操作を明示的に使う。

Danbooruで作者が複数いる場合は、投稿の出典URLにあるTwitterアカウントを全作者へ割り当てない。Twitterのアカウントに結び付けるのは、作者が一人である場合だけとする。APIから取得するプレビューの出典には、周囲のページの別投稿のDOM情報を混ぜない。

## 移行とバックアップ

`0030_small_impossible_man.sql` は旧 `authors.account_id` の非空値を、既存アカウントに同じ値がない場合に `platform = NULL` のアカウントへ退避してからカラムを削除する。不明なプラットフォームや固定IDを推測せず、重複した未確認情報も保持する。既存の外部アカウントの表示名は作者名から初期化する。

本番での適用はサーバーを新スキーマへ切り替えるタイミングに合わせ、PostgreSQLでは `bun run --cwd apps/server db:migrate`、PGliteでは `bun run --cwd apps/server db:migrate:pglite` を実行する。PGliteの保存先を変更している場合は `PGLITE_DATA_DIR` も実際のサーバーと合わせる。旧サーバーは削除されたカラムを参照するため、旧バージョンを並行稼働させない。

バックアップは一人の作者に属する全外部アカウントと固定ID・プロフィール・取得日時を保存する。復元時に同じ外部アカウントが別の作者に紐づいていた場合は、勝手に作者を統合せずエラーにする。作者管理で関係を確認してから統合する。

## 運用上の限界

固定IDなしの旧データは自動で正しい作者に判定できない。旧handleに対する現在のプロフィール照会だけでは、過去の投稿者の本人確認にならない。出典投稿の投稿者IDや、ユーザーが確認した情報を修正の根拠にする。

外部プロフィールの変更は新しい取り込みで観測した際に反映する。バックグラウンドで全アカウントを巡回する処理はない。表示名を使う既存の検索条件・プリセットは、管理名変更後に見直しが必要な場合がある。検索条件の作者UUID化は別の変更として扱う。
